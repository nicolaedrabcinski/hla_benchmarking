## 2a. Font-rendering fix (2026-07-22, follow-up pass)

Nick found that despite `sns.set_theme(font="sans-serif")` in all three
scripts, every one of the five figures was actually rendering in
matplotlib's bundled **DejaVu Sans Bold** — visibly chunkier/bolder than the
Arial-equivalent look expected for an academic/journal figure.

**Root cause:** `font="sans-serif"` is a *generic* family name that
matplotlib's font manager resolves via its own font cache. 'Liberation Sans'
(a free, metric-compatible clone of Arial) IS installed on this machine at
`/usr/share/fonts/truetype/liberation/LiberationSans-*.ttf` (confirmed via
`fc-list`), but matplotlib does not scan/index every system font
automatically, so `findfont("Liberation Sans")` fails to find it unless the
font file is explicitly registered with
`matplotlib.font_manager.fontManager.addfont(...)` first — without that
call, resolution silently falls through to matplotlib's own bundled DejaVu
Sans.

**A second, subtler bug found while fixing the first:** the natural
implementation calls the addfont/rcParams fix *before* `sns.set_theme()`.
That is wrong and fails silently: `sns.set_theme(..., font="sans-serif",
...)` itself overwrites `rcParams['font.sans-serif']` with seaborn's own
default list (empirically: `['Arial', 'DejaVu Sans', 'Liberation Sans',
'Bitstream Vera Sans', 'sans-serif']`), which puts `'Arial'` *ahead* of
`'Liberation Sans'`. Since real Arial is not installed here, that reorders
resolution straight past Liberation Sans to DejaVu Sans — the fix looks like
it ran (no error) but is actually inert. Confirmed by direct `rcParams`
inspection both call orders; see `notebooks/fig7_style_common.py` docstring
for the full reproduction.

**Fix, and where it lives:** a new shared module,
`notebooks/fig7_style_common.py`, provides one function,
`register_fonts()`, called by all three scripts' `apply_theme()`
IMMEDIATELY AFTER `sns.set_theme(...)` (not before). It:
1. Calls `fontManager.addfont()` on `LiberationSans-{Regular,Bold,Italic,
   BoldItalic}.ttf` (guarded so the disk scan runs only once per process,
   safe to call many times);
2. Sets `rcParams['font.family'] = "sans-serif"` and
   `rcParams['font.sans-serif'] = ["Liberation Sans", "Arial", "DejaVu
   Sans"]` **unconditionally on every call** (not behind the addfont guard —
   each script calls `apply_theme()` once per figure, and `sns.set_theme()`
   re-clobbers this rcParam every time, so skipping the reassignment on the
   2nd+ call would have silently regressed every figure after the first one
   produced per script run back to DejaVu Sans. This exact regression was
   caught during testing and is why the guard is scoped the way it is.).

This was previously a genuine three-way duplication risk (each script would
otherwise have needed its own copy of this fix) — `fig7_style_common.py` is
now the single source for it, imported by all three scripts, matching this
agent's mandate to never fork a shared fix locally.

**Graceful fallback on a machine without Liberation Sans** (e.g. a fresh
checkout on a different OS/container): `register_fonts()` does not raise if
the font files are missing — it prints a one-line note and lets the
`font.sans-serif` fallback chain (`Liberation Sans → Arial → DejaVu Sans`)
resolve to whatever IS installed, so the pipeline still renders a figure
(with matplotlib's default DejaVu Sans, not erroring the run) rather than
crashing on a font that doesn't exist there. To restore the exact intended
look on such a machine, install the `fonts-liberation` package (or
equivalent) and re-run.

**Verification performed (not just visual):**
- Programmatic: `matplotlib.font_manager.findfont(FontProperties(family=
  ["sans-serif"]))` was confirmed to resolve to
  `/usr/share/fonts/truetype/liberation/LiberationSans-Regular.ttf` (and
  `-Bold.ttf` for bold weight) after each script's `apply_theme()` runs —
  checked individually for all three scripts, and re-checked after a second
  `apply_theme()` call within the same process to rule out the regression
  described above (both calls PASS).
- Visual: re-rendered PNGs show visibly thinner, more open letterforms than
  the previous DejaVu Sans Bold rendering (checked on the dense heatmap panel
  a and the slope plot panel e — both legible at 300 DPI).
- All five figures (10 files: 5×PNG+SVG) were regenerated from the current
  scoring-pipeline output (`results/allele_miscall_by_dataset.csv` and its
  derived tables — unchanged by this pass) using
  `python notebooks/fig7_per_dataset_miscall.py`,
  `python notebooks/fig7_per_dataset_top_alleles.py`, and
  `python notebooks/fig7_miscall_variants.py`. All three exited 0. Printed

  scorable in ≥2 datasets; etc.) are unchanged from the pre-fix run recorded

**Title/label weight was reviewed at the same time** (Nick's request) and

## 2b. ggplot2 theme pivot (2026-07-22, second follow-up pass, at Nick's explicit request)

Nick's feedback on the §2/§2a "Nature-style" theme (white panel background,
open axes, no grid) was that it did not read as "real academic style" —
specifically: **"должно быть похоже на графики сделанные в ggplot2"** (should
look like graphs made in ggplot2). The white/open-axes look is a legitimate
academic convention (Nature/Cell house style), but it is not what "ggplot2"
means visually, and the request was for the latter, implemented for real
rather than asserted.

**What changed, concretely:**
- `fig7_style_common.apply_ggplot_theme()` replaces
  `sns.set_theme(..., style="white", ...)` + manual rcParams as the theme
  entry point for all three scripts. It layers matplotlib's built-in
  `'ggplot'` style sheet with explicit overrides for the three visually
  load-bearing traits of ggplot2's default `theme_gray()`:
  1. **Panel background** `#EBEBEB` (grey92), no visible axis border box —
     the grey fill itself reads as the panel boundary, exactly as in R.
  2. **Gridlines white-on-grey**, drawn on top of the panel fill, not
     grey-on-white.
  3. **`facet_wrap()`-style strip labels**: a solid darker-grey (`#D9D9D9`)
     rectangle spanning the top of each small-multiple panel, bold centered
     text — added via the new `facet_strip()` helper, since matplotlib/
     seaborn have no built-in equivalent. This replaces the plain
     `ax.set_title()` calls used in panels b and c.
- `register_fonts()` (§2a) is called from inside `apply_ggplot_theme()`,
  after `plt.style.use('ggplot')`, for the same clobber-order reason as
  before — style sheets overwrite `font.sans-serif` wholesale, same as
  `sns.set_theme()` did.
- Panel c's `PANEL_PAD_TOP` was widened (0.52in → 0.66in) to make room for
  the taller strip + subtitle stack; verified visually, no clipping.
- `sns.despine()` calls were left in place (now a no-op — there is no border
  to hide once `axes.edgecolor` matches the panel fill) rather than removed,
  to keep the diff minimal.

**Verified:** all three scripts re-ran clean (exit 0), all 5 PNG+SVG pairs
regenerated, console-printed data/counts unchanged (confirms this is a
render-only change, same as §2a). Visually confirmed on all five panels:
grey facet backgrounds, white gridlines, grey strip headers with locus-colored
bold text on panels b/c; consistent grey/white grid on the single-axes panels
a/d/e.

**Update (same day, third follow-up):** the ColorBrewer Set1 locus palette
above was itself replaced after Nick flagged it ("палитра плохая") — it is
recognizably *not* what ggplot2 produces by default, and that mismatch (not
just background/grid) is what "should look like ggplot2" meant. Replaced with
ggplot2's actual default discrete scale, `scales::hue_pal()(5)` (evenly spaced
HCL hues, chroma=100, luminance=65, hue offset 15°), confirmed against the
ggplot2/scales documentation: `A #F8766D, B #A3A500, C #00BF7D,
DQB1 #00B0F6, DRB1 #E76BF3`, assigned in ggplot2's own alphabetical
factor-level order (A, B, C, DQB1, DRB1 — note DQB1 < DRB1 alphabetically).
Applied identically in all three scripts' `palette` dicts. This *is* now a
per-locus-color change, unlike the background/grid pivot above — logged here
rather than silently overriding §4's now-superseded CVD-simulation note (a
fresh accessibility check against this palette has not yet been run).

**Also changed:** panel b was cut from 20 facets (one per pooled-top-20
allele) to the 6 alleles that are actually scorable (≥6 evaluable calls) in

## 2d. Panel c split into 7 standalone files (2026-07-23, at Nick's request: "сделай график C разделенным а не панель")

Panel c was previously one composite image (`miscalled_alleles_top_per_dataset.png`)
laying out all 7 datasets' own-ranking bar charts as small multiples in a
3-column grid, with a shared suptitle/legend/panel-letter. That file is
**removed** (it was untracked, never committed, safe to delete) and replaced

figures, each full-size with its own title, axis, and one-row Locus legend.
Datasets with 0 rankable alleles would be skipped (none currently are).

Bar height (`BAR_H`), title/subtitle styling (`facet_strip()`), and the
raw-count bar-end annotations are all unchanged from the small-multiples
version, so a single dataset's chart looks the same whether compared against
the old composite or on its own. The old multi-panel-only sizing constants
(`_panel_height()`, `V_GAP`, `FIG_TOP_PAD`, `FIG_BOT_PAD`, `FIG_SIDE_PAD`,
`add_panel_label()`) were deleted as dead code rather than left unused.

**Bug found and fixed during this pass:** the first version of
`plot_single_dataset()` sized the title-strip/subtitle offset as a fraction of
*figure* height, carried over unchanged from the composite version where every
subplot shared one uniform grid cell size. Once each dataset got its own
figure sized to its own bar count, that fraction meant something different at
n=20 (D1, D3, D7) than at n=2 (D5) — small panels rendered with the title
overlapping the subtitle/legend. Fixed by sizing the strip/subtitle offset in
inches divided by the *axes* height (`n * BAR_H`), which is what
`ax.transAxes` actually scales against, giving every dataset the same
0.30in physical strip height regardless of n. Verified visually on the
smallest (D5, n=2) and largest (D1/D7, n=20) panels after the fix.

Panel c no longer carries a single-letter panel label (`add_panel_label`) —
labelling 7 separate files "c" would be ambiguous. If the manuscript needs
per-file identifiers, `scientific-writer` should decide the convention
(e.g. "c1"–"c7", or by dataset name) when drafting the caption; not decided
here.
